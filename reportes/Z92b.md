## Paso 1, relevamiento
- **De dónde sale "sin configuración de LiveKit":** de una sola línea, `lib/vivo/publicarLiveKit.ts:25` (antes del cambio), dentro de `pedirToken`: `if (r.status === 503) return { ok: false, motivo: "sin configuración de LiveKit" }`. Esa línea corre después de que `fetch("/api/livekit/token")` recibió una respuesta 503.
- **Variables que lee el cliente:** ninguna. Ni `publicarLiveKit.ts` ni `liveKitCiclo.ts` usaban `process.env`, y la URL ya llegaba en la respuesta `{ token, url }`.
- **Variables que leía la ruta:** `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET`, `NEXT_PUBLIC_LIVEKIT_URL` y la opcional `LIVEKIT_SALA`. Si faltaba cualquiera de las tres primeras, contestaba 503.
- **Dónde se corta el flujo:** el cliente no se corta antes de pedir el token. La secuencia es "Compartir" → `publicarLiveKit` → `PublicadorLiveKit.iniciar` → `pedirToken` → `fetch` → 503 → `falla("sin configuración de LiveKit")` → `sin_conexion`. Ese texto implica que hubo un pedido. Si no aparece en Network, lo más probable es que DevTools se haya abierto después del pedido (Network solo registra con el panel abierto) o que haya un filtro activo; el pedido es un POST que se llama `token`.
- **Dónde sí estaba tu hipótesis:** del lado del servidor. Next reemplaza `process.env.NEXT_PUBLIC_*` por su valor al compilar, también en el código de las rutas.
  - Con `next build` en Docker, `.dockerignore` excluye `.env*` y el `Dockerfile` no pasa esa variable como `ARG`, así que la ruta quedaba con la URL vacía y daba 503 siempre, aunque el contenedor la tuviera al correr.
  - En el compose local (`next dev`), el valor se toma del entorno cargado al arrancar. Por eso el 503 local apunta a que alguna de las tres variables no estaba disponible para el proceso de Next cuando arrancó el contenedor: no está en `frontend/.env.local` ni en `frontend/.env`, está en otro archivo, el nombre no coincide, o se agregó con el contenedor andando. No abrí los `.env*`; solo vi que en `frontend/` existen `.env`, `.env.local` y `.env.example`.
